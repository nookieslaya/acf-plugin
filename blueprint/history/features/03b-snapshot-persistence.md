# Feature: Snapshot persistence

**From build-plan:** feature 3b
**Status:** complete

## Goal

Persist immutable normalized-schema snapshots in a dedicated WordPress table
and retrieve them through a small plugin-owned repository. This creates the
durable comparison input for later capture and diff features without adding
Admin UI, CLI commands, schema capture orchestration, or comparisons.

## In scope

- An immutable `SchemaSnapshot` contract with a UUID, non-empty source ID,
  UTC creation time, schema version, and canonical schema array.
- A dedicated `${wpdb->prefix}acf_schema_guard_snapshots` table installed on
  plugin activation through `dbDelta()`.
- Append-only repository methods to insert a snapshot, fetch one by ID, and
  fetch the latest snapshot for one source ID.
- Strict JSON serialization on write and decoding plus schema-version checks on
  read; malformed or unsupported persisted records fail explicitly rather than
  returning ambiguous data.
- A lazy plugin seam for the repository, available to feature 3c.
- Isolated PHP assertions for the snapshot contract and repository boundary,
  plus syntax validation for all plugin PHP files.

## Out of scope

- Capturing the live ACF runtime, choosing a source ID automatically, hashes,
  retention, deletion, updates, comparisons, risk rules, Admin screens,
  WP-CLI, REST routes, settings, or writes to `wp_options`.
- Migrating or importing any existing data. The table begins empty.
- Storing PHP serialized schema payloads or querying inside a JSON payload.

## Build loop

Build one small reviewed step at a time. Each step must leave the plugin safe
when ACF is absent and must not create a snapshot unless a later caller asks the
repository to insert one.

## Build steps

- [x] **Step 1 - Immutable snapshot contract** - add the snapshot value object
  and repository interface with strict input validation and canonical schema
  payload handling. *Done when:* a valid snapshot round-trips through its row
  representation and invalid identifiers, source IDs, dates, or schema versions
  are rejected without WordPress globals.
- [x] **Step 2 - Table installer** - add the dedicated table definition and a
  plugin activation hook that installs or upgrades it through `dbDelta()`.
  *Done when:* the SQL contains a UUID primary key, source/time lookup index,
  schema version, JSON payload, UTC timestamp, and the installer has no effect
  outside explicit activation.
- [x] **Step 3 - WordPress snapshot repository** - add append-only insert,
  find-by-ID, and latest-for-source behavior using `$wpdb` with prepared reads.
  *Done when:* writes use only the dedicated table, a failed database operation
  is explicit, and reads reconstruct the immutable contract or return `null` for
  an absent row.
- [x] **Step 4 - Plugin seam and deterministic verification** - expose the
  repository via the plugin service, document the storage contract, and add
  focused isolated assertions plus `php -l`. *Done when:* feature 3c can obtain
  one repository service without touching the table until it creates a snapshot.

## Data / contracts

This is a load-bearing contract for features 3c and 4.

### `SchemaSnapshot`

- `id` - lowercase UUID generated by `wp_generate_uuid4()` at a later capture
  boundary or supplied by tests; it is never reassigned or updated.
- `source_id` - caller-provided, non-empty identifier with at most 191 bytes.
- `schema_version` - integer copied from `schema['schema_version']`; version `1`
  is the only accepted version in this feature.
- `schema` - canonical array returned by `NormalizedSchema::to_array()`.
- `created_at` - UTC `Y-m-d H:i:s`, supplied by the caller or generated by a
  later capture boundary; it is immutable.

### Table

`{$wpdb->prefix}acf_schema_guard_snapshots`:

- `id char(36) NOT NULL` - primary key.
- `source_id varchar(191) NOT NULL`.
- `schema_version smallint unsigned NOT NULL`.
- `schema longtext NOT NULL` - canonical JSON only.
- `created_at datetime NOT NULL` - UTC.
- index `(source_id, created_at)` for latest-per-source lookups.

The repository may insert rows only. There is intentionally no update or delete
method, and snapshot schemas are never placed in `wp_options`.

## Testing

No project test runner is configured. Add standalone PHP assertion scripts:

- validate contract round-tripping, invalid input, and stable JSON payloads
  without WordPress or database access;
- use a narrow fake `$wpdb` boundary to verify the repository uses its dedicated
  table, performs insert-only writes, and returns `null` for missing snapshots;
- inspect the generated table SQL in isolation where practical;
- run `php -l` for every plugin PHP file.

The local CLI cannot connect to the WordPress database, so the real activation
and table creation path remains a manual verification after implementation.

## Notes for the AI

- Use PHP 7.4-compatible syntax and WordPress APIs only.
- The persistence layer must not require ACF or read `acf-json`.
- Keep SQL ownership in one class. Use `$wpdb->prefix`, `$wpdb->get_charset_collate()`,
  and `dbDelta()` only during the activation hook.
- Reject malformed persisted JSON and unsupported schema versions with a clear
  `RuntimeException`; do not silently coerce data or drop fields.
- Use prepared SQL for all reads. `$wpdb->insert()` is acceptable for the fixed
  table insert with explicit formats and error checking.
- Do not add a public capture method yet. Feature 3c constructs snapshots from
  `normalized_schema()` and asks this repository to store them.
